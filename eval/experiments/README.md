# Конфіги експериментів

Файл для `localmind eval --dataset <тека> --config <файл>`. Кожен прогін може задати власні нарізку й модель:

```json
{"name": "e3-128", "modes": ["hybrid"], "k": 10,
 "chunking": {"strategy": "fixedSize", "chunkSizeTokens": 128, "overlapPercent": 15},
 "model": "multilingual-e5-base"}
```

| Поле | Значення |
|---|---|
| `chunking.strategy` | `fixedSize` або `paragraph`; не вказано — з конфігурації (`LocalMind:Chunking`) |
| `chunking.chunkSizeTokens` | розмір фрагмента в токенах; не більший за ліміт моделі |
| `chunking.overlapPercent` | перекриття, % від розміру фрагмента (0–50) |
| `model` | назва з каталогу `LocalMind:ModelCatalog` (DR-024); модель має бути завантажена: `scripts/download-models <модель>` |

Усі поля `chunking` необов'язкові, без `chunking` і `model` береться конфігурація за замовчуванням.
Прогони з однаковою *ефективною* комбінацією нарізки й моделі ділять один індекс: відсутній `chunking`, порожній
`"chunking": {}`, явно вказані значення за замовчуванням і назва моделі за замовчуванням у будь-якому регістрі — це одна
комбінація. Для кожної іншої комбінації корпус індексується заново у власній тимчасовій базі (бібліотека користувача не
чіпається), тож вона займає ще стільки ж часу й місця на диску.

## Перевірка до старту, часткові результати

Перед першим прогоном перевіряються **всі** комбінації: модель є в каталозі, `chunkSizeTokens` не більший за ліміт моделі
(у `paraphrase-*` 128) і більший за резерв під префікс, файли моделі завантажені. Усі знайдені проблеми друкуються разом,
і нічого не запускається — довгий експеримент не впаде в останній комбінації. Після кожної комбінації CSV і Markdown
перезаписуються (разом з усіма попередніми), тож якщо запуск перервали, результати вже на диску. Рядки в обох файлах
йдуть у порядку прогонів конфігу, у Markdown-таблиці є колонки моделі й нарізки.

## Порівнянність замірів

- **Час індексації.** Перед вимірюванням виконується прогрів (JIT, SQLite, кеш файлів) на крихітному корпусі, який
  відкидається, тож перша комбінація не «холодніша» за наступні. Невеликі відхилення (десяті частки секунди) лишаються.
- **Пікова пам'ять** — пік усього процесу (ОС не дає скинути його між комбінаціями), тому вона не зменшується від
  комбінації до комбінації й залежить від порядку: у пізніших вона не менша, ніж у попередніх, навіть якщо їх власний
  розхід менший. Для чесного порівняння пам'яті комбінацій запускайте їх окремими викликами `eval` (окремий конфіг на
  кожну). Розмір бази й кількість фрагментів — власні для комбінації.

Приклади:

- [`e2.json`](e2.json) — порівняння чотирьох моделей каталогу при однаковому розмірі фрагмента (120 токенів: у
  `paraphrase-*` ліміт 128);
- [`e3.json`](e3.json) — розмір фрагмента 128/256/512 × перекриття 0/15 % (6 комбінацій) на моделі за замовчуванням; стратегію `paragraph` і розміри 64 чи перекриття 30 % можна додати рядками в конфіг, але кожна нова комбінація — ще одна повна індексація.
  Орієнтир за часом: на підкорпусі ~800–1000 документів одна індексація триває ≈ 15–20 хв, тож E3 — це ≈ 1,5–2 години, E2 з чотирма моделями — стільки ж, а на повному корпусі (~6,4 тис. документів) одна індексація 2–2,5 год.

```bash
dotnet run --project src/LocalMind.Cli -c Release -- eval --dataset eval/datasets/demo --config eval/experiments/e3.json
```

У CSV кожен рядок має колонки `model`, `chunking`, `chunk_size_tokens`, `overlap_percent` (фактичні значення корпусу),
а також `documents`, `chunks`, `index_seconds`, `db_bytes` для цього корпусу — за ними `eval/plots` групує E2 і E3.
