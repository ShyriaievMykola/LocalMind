# Лог рішень

Архітектурні та технічні рішення проєкту у форматі «проблема → варіанти → рішення».
Нове рішення додається в кінець файла з наступним номером. Рішення не видаляються: якщо рішення змінилось,
додається новий запис, а старий отримує статус «замінено DR-NNN».

**Шаблон запису:**

```markdown
## DR-NNN · Коротка назва
**Дата:** РРРР-ММ-ДД · **Статус:** прийнято · **Issue:** #N

**Проблема.** Що треба вирішити і чому.
**Варіанти.** Які були альтернативи.
**Рішення.** Що обрали.
**Чому / наслідки.** Аргументи і що з цього випливає.
```

---

## DR-001 · Avalonia UI для десктопного застосунку

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Потрібен GUI-фреймворк, який працює на Windows, Linux і macOS з одного коду.

**Варіанти.** .NET MAUI; WPF; Avalonia UI.

**Рішення.** Avalonia UI з MVVM (CommunityToolkit.Mvvm).

**Чому / наслідки.** MAUI офіційно не підтримує Linux, WPF працює лише на Windows. Avalonia дає один XAML/MVVM-код
для всіх трьох ОС, а підхід (XAML, binding, commands) близький до MAUI, який вивчається в курсі.
MAUI вимагається лише в індивідуальній ЛР4, а не в проєкті.

## DR-002 · .NET 10 (LTS)

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Вибір версії платформи.

**Варіанти.** .NET 8 (LTS), .NET 9 (STS), .NET 10 (LTS).

**Рішення.** .NET 10, версія SDK закріплена в `global.json`.

**Чому / наслідки.** Актуальна LTS-версія з підтримкою до 2028 р. Однакова версія SDK у всіх учасників і в CI.

## DR-003 · SQLite + EF Core, FTS5 через raw SQL

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Потрібне локальне сховище для документів, фрагментів, embeddings і повнотекстового індексу.

**Варіанти.** SQLite через Microsoft.Data.Sqlite (+ Dapper); SQLite через EF Core; окремий сервер БД (PostgreSQL).

**Рішення.** SQLite через EF Core (сутності, міграції, обмеження цілісності); FTS5-таблиця і BM25-запити — параметризованим raw SQL.

**Чому / наслідки.** Один файл без сервера відповідає принципу local-first. EF Core дає міграції, PK/FK та індекси
(критерій C5, ЛР1 курсу). EF Core не підтримує віртуальні таблиці FTS5, тому для них — SQL у міграції
та параметризовані запити (захист від ін'єкцій).

## DR-004 · Локальні embeddings через ONNX Runtime

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Обчислення embeddings без хмарних сервісів і без Python.

**Варіанти.** ONNX Runtime у .NET-процесі; Ollama; окремий Python-сервіс.

**Рішення.** ONNX Runtime + Microsoft.ML.Tokenizers, інференс на CPU.

**Чому / наслідки.** Модель працює прямо в застосунку, без зовнішніх процесів і мережі. Моделі не зберігаються
в Git — завантажуються скриптом з перевіркою хешу.

## DR-005 · Hybrid search: BM25 + semantic, злиття RRF

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Семантичний пошук погано знаходить точні терміни (коди помилок, назви функцій, версії),
а пошук за ключовими словами — перефразування і міжмовні запити.

**Варіанти.** Лише semantic; лише BM25; комбінація зі зваженою сумою оцінок; комбінація через Reciprocal Rank Fusion.

**Рішення.** Три режими (keyword, semantic, hybrid); hybrid зливає списки методом RRF.

**Чому / наслідки.** RRF працює з рангами, а не з оцінками, тому не потребує нормалізації різних шкал.
Яке з рішень краще на наших даних — перевіряється в експерименті E1.

## DR-006 · Спершу точний векторний пошук, потім HNSW

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Пошук найближчих векторів має бути швидким на великих базах.

**Варіанти.** Одразу approximate-індекс (HNSW); точний перебір (brute-force).

**Рішення.** Спершу brute-force, згодом HNSW за тим самим інтерфейсом `IVectorIndex`.

**Чому / наслідки.** Точний перебір простий і є еталоном точності. HNSW додаємо, коли є з чим порівнювати;
межа, з якої він вигідніший, — предмет експерименту E4.

## DR-007 · Бекап із шифруванням на клієнті (zero-knowledge)

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Користувач хоче резервну копію поза своїм комп'ютером, але нотатки — особисті дані.

**Варіанти.** Сервер зберігає дані у відкритому вигляді під захистом автентифікації; дані шифруються на клієнті до відправки.

**Рішення.** Шифрування на клієнті; сервер зберігає лише шифротекст і не має ключа.

**Чому / наслідки.** Злам сервера не розкриває нотатки; узгоджується з принципом local-first.
Наслідки: сервер не може шукати по даних, а забутий пароль шифрування означає втрату бекапу.
Це прийнятно, бо пошук завжди локальний.

## DR-008 · PBKDF2 + AES-GCM із вбудованої криптографії .NET

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Вибір алгоритмів виведення ключа з пароля і шифрування бекапу.

**Варіанти.** Argon2id (стороння бібліотека) або PBKDF2 (вбудований); AES-GCM (вбудований) або libsodium.

**Рішення.** PBKDF2-HMAC-SHA256 (≥600 000 ітерацій, випадкова сіль) + AES-256-GCM; формат конверта з номером версії.

**Чому / наслідки.** Вбудовано в платформу, працює на всіх ОС без нативних залежностей. GCM забезпечує
не лише конфіденційність, а й виявлення підміни. Версія формату дозволяє згодом перейти на Argon2id без втрати старих бекапів.

## DR-009 · Автентифікація: ASP.NET Core Identity + JWT + refresh-токени

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Сервер бекапу має знати, чиї дані він зберігає, і не віддавати їх іншим.

**Варіанти.** Identity + JWT + refresh-токени; власний OAuth2/OIDC-сервер (OpenIddict) з PKCE.

**Рішення.** Identity + короткоживучий JWT access-токен + refresh-токен з ротацією та відкликанням.

**Чому / наслідки.** Значно простіше за OIDC при достатньому рівні безпеки для проєкту. OIDC — можливе розширення,
якщо дозволить час або вимагатиме дисципліна «Захист програм і даних».

## DR-010 · П'ять проєктів у solution замість окремого проєкту на кожен модуль

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** Початкова структура мала ~16 проєктів (Storage, Security, Sync, Contracts, Eval, Benchmarks…),
що завелико для команди з 4 людей.

**Варіанти.** Окремий проєкт на кожен модуль; мінімальний набір проєктів, модулі — папками.

**Рішення.** `Core`, `Search`, `App`, `Cli`, `Server` + тестові проєкти. Модулі всередині — папками.

**Чому / наслідки.** Менше накладних витрат на налаштування і залежності. Зони відповідальності видно з issue,
міток `area:*` і PR. Папку виносимо в окремий проєкт, лише коли вона справді розрослась.

## DR-011 · Централізоване керування версіями NuGet

**Дата:** 2026-10-12 · **Статус:** прийнято

**Проблема.** У різних проєктах можуть опинитися різні версії одного пакета.

**Варіанти.** Версії в кожному `.csproj`; Central Package Management (`Directory.Packages.props`).

**Рішення.** Central Package Management: версії лише в `Directory.Packages.props`, у `.csproj` — без `Version`.

**Чому / наслідки.** Одна версія пакета на весь solution, оновлення в одному місці, простіше для Dependabot.

## DR-012 · Явне підняття транзитивної залежності Microsoft.OpenApi

**Дата:** 2026-10-23 · **Статус:** прийнято · **Issue:** #2

**Проблема.** Шаблон webapi через `Microsoft.AspNetCore.OpenApi` 10.0.10 підтягує транзитивну залежність
`Microsoft.OpenApi` 2.0.0 з відомою вразливістю високого рівня (GHSA-v5pm-xwqc-g5wc).
У режимі CI попередження NU1903 ламає збірку.

**Варіанти.** Придушити попередження; чекати оновлення `Microsoft.AspNetCore.OpenApi`; явно вказати виправлену версію.

**Рішення.** Явний `PackageReference` на `Microsoft.OpenApi` 2.7.5 (перша виправлена версія гілки 2.x).

**Чому / наслідки.** Придушення приховує реальну вразливість. Явне підняття версії усуває її одразу.
Dependabot оновлює цей пакет разом з групою ASP.NET Core, щоб версії не розійшлись.

## DR-013 · Microsoft.OpenApi лише в гілці 2.x

**Дата:** 2026-10-23 · **Статус:** прийнято · **Issue:** #16

**Проблема.** Dependabot (PR #11) підняв `Microsoft.OpenApi` з 2.7.5 до 3.11.0. `Microsoft.AspNetCore.OpenApi` 10.x
вимагає `>= 2.12.2 && < 3.0.0`, тому `LocalMind.Server` перестав компілюватися (помилки в згенерованому коді OpenAPI
та NU1608). PR змерджили без перевірки, бо CI ще не було.

**Варіанти.** Відкотити PR #11 повністю; залишити 3.x і чекати сумісного `Microsoft.AspNetCore.OpenApi`;
повернути найновішу 2.x і заборонити мажорні оновлення цього пакета.

**Рішення.** `Microsoft.OpenApi` 2.13.0 (найновіша 2.x, не має вразливості з DR-012); у `dependabot.yml` —
`ignore` для мажорних оновлень `Microsoft.OpenApi`. Одночасно додано CI, який перевіряє кожен PR.

**Чому / наслідки.** Інші оновлення з PR #11 коректні, відкочувати їх не потрібно. Обмеження на мажорну версію
знімемо, коли вийде `Microsoft.AspNetCore.OpenApi` із підтримкою 3.x. Урок: PR від Dependabot мерджимо лише з зеленим CI.

## DR-014 · Формат зашифрованого бекапу v1

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #76

**Проблема.** Потрібні конкретні параметри DR-008 і бінарний формат файла, який клієнт шифрує, а сервер лише зберігає.

**Варіанти.** JSON з base64-полями; власний бінарний конверт; потоковий формат із шифруванням блоками.

**Рішення.** Бінарний конверт `"LMBK" | version (1 байт) | salt (16) | nonce (12) | ciphertext | tag (16)`.
Ключ — PBKDF2-HMAC-SHA256, 600 000 ітерацій, 32 байти; шифр — AES-256-GCM. Сіль і nonce нові для кожного бекапу.
Заголовок (magic, версія, сіль, nonce) передається в GCM як associated data.

**Чому / наслідки.** Бінарний формат без накладних витрат base64. Параметри KDF прив'язані до версії, тож у файлі
їх не зберігаємо, а нова версія (Argon2id, більше ітерацій) не ламає старі бекапи. Через AAD підміна заголовка
(наприклад, версії) виявляється так само, як і зміна шифротексту. AES-GCM у .NET не потоковий, тому бекап
шифрується цілим у пам'яті — прийнятно, бо розмір бекапу обмежений лімітом сервера; потоковий формат (блоки з власними
nonce) — можлива версія 2. Неправильний пароль і пошкоджений файл дають ту саму помилку.
Пароль перед PBKDF2 нормалізується в Unicode NFC — інакше той самий пароль із літерою «й», введений на macOS (NFD)
і на Windows (NFC), давав би різні ключі.

## DR-015 · SQLite як база сервера бекапу

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #77

**Проблема.** Серверу потрібна база для користувачів Identity, refresh-токенів і метаданих бекапів.

**Варіанти.** PostgreSQL в окремому контейнері; SQLite-файл поруч із сервером.

**Рішення.** SQLite через EF Core, як і на клієнті (DR-003). Міграції застосовуються під час старту сервера.
Самі бекапи лежать у файловій системі, у базі — лише метадані.

**Чому / наслідки.** Сервер — один процес для невеликої кількості користувачів, окремий сервер БД тут лише
ускладнює розгортання й тести (інтеграційні тести йдуть на in-memory SQLite). Один стек EF Core для клієнта й сервера.
Горизонтальне масштабування неможливе без переходу на PostgreSQL — EF Core робить цей перехід відносно дешевим.

## DR-016 · Політика паролів облікового запису

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #77

**Проблема.** Стандартна політика Identity (6 символів + цифра, великі/малі літери, спецсимвол) підштовхує до
коротких передбачуваних паролів на кшталт `Passw0rd!`.

**Варіанти.** Стандартна політика Identity; довжина без правил складу (NIST SP 800-63B).

**Рішення.** Мінімум 12 символів і щонайменше 4 різні символи, без вимог до складу. Після 5 невдалих спроб входу —
блокування на 15 хвилин. Неправильний пароль, неіснуючий email і заблокований обліковий запис дають однакову
відповідь `401`; для неіснуючого email і заблокованого акаунта пароль усе одно хешується, щоб час відповіді не видавав,
чи є такий користувач. Пароль не може містити email (контекстне слово за NIST). Логін — email, тож дозволені
й кириличні адреси; повідомлення Identity — українською.

**Чому / наслідки.** Довжина сильніше впливає на стійкість, ніж правила складу, і дозволяє парольні фрази.
Спершу реєстрація повідомляла `409`, якщо email зайнятий; з DR-032 вона відповідає так само, як на нову адресу.

## DR-017 · Access-токени JWT і зберігання секретів сервера

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #78

**Проблема.** Захищеним ендпоінтам потрібен access-токен, а ключ його підпису не може лежати в репозиторії.

**Варіанти.** HS256 зі спільним секретом; RS256/ES256 з парою ключів; ключ в `appsettings.json`, user-secrets,
змінні оточення, сховище секретів (Key Vault).

**Рішення.** JWT HS256 зі строком дії 15 хв, перевіряються підпис, `iss`, `aud`, `exp` (допуск 30 с), дозволено
лише алгоритм HS256. Ключ `Jwt:SigningKey` — base64, ≥ 32 байти після декодування (пароль замість ключа не пройде), у Development через `dotnet user-secrets`, у Docker —
змінна оточення `Jwt__SigningKey`. Без ключа сервер не стартує (валідація опцій на старті).

**Чому / наслідки.** Токени видає і перевіряє той самий сервер, тож асиметричні ключі нічого не дають.
Фіксований список алгоритмів закриває атаки з `alg: none` і підміною алгоритму. Помилка конфігурації видна одразу,
а не першим запитом. Причина відмови токена (`error_description` у `WWW-Authenticate`) віддається лише в Development. Локальний запуск: `dotnet user-secrets set Jwt:SigningKey "$(openssl rand -base64 48)" --project src/LocalMind.Server`.

## DR-018 · Refresh-токени: хеш, ротація, виявлення повторного використання

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #79

**Проблема.** Access-токен живе 15 хв; клієнту потрібно оновлювати його без пароля, а вкрадений refresh-токен
не повинен давати доступ назавжди.

**Варіанти.** Довгоживучий refresh-токен без ротації; ротація без виявлення повторного використання;
ротація + відкликання всієї сесії при повторному використанні (OAuth 2.0 Security BCP).

**Рішення.** Refresh-токен — 32 випадкові байти (base64url), строк 14 днів. У БД — лише SHA-256 (токен має повну
ентропію, тож сіль і повільний хеш не потрібні). Кожен `POST /auth/refresh` гасить старий токен і видає новий у тій
самій сесії (`SessionId`). Повторне пред'явлення вже використаного токена відкликає всю сесію — і зловмисника, і
справжнього клієнта, який після цього входить знову. Гасіння атомарне (`UPDATE … WHERE ConsumedAt IS NULL`), тож
з двох одночасних запитів з тим самим токеном успішний лише один. `POST /auth/logout` відкликає сесію і завжди
відповідає `204`.

**Чому / наслідки.** Злив БД не дає чинних токенів; вкрадений токен працює лише до першого оновлення справжнім клієнтом.
Відкликання сесії чи зміна пароля не впливає на вже видані access-токени — вони діють до 15 хв; для проєкту
це прийнятно. Сесія недійсна й відкликається, якщо змінився
SecurityStamp користувача (зміна пароля), акаунт заблоковано, а також через 30 днів від входу за паролем, хоч би
скільки разів її оновлювали. `RevokeAllAsync` відкликає всі сесії користувача. Старі записи токенів поки не чистимо.
## DR-019 · Keyword-пошук: FTS5 з external content, слова через OR і префікс за основою

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #73

**Проблема.** Потрібен BM25-пошук по фрагментах, що працює з українськими словоформами і не ламається від
синтаксису FTS5 у запиті користувача.

**Варіанти.** Окрема FTS-таблиця з копією тексту; external content (`content='Chunks'`) з тригерами.
Слова запиту через AND (за замовчуванням FTS5) або через OR. Точні слова або префікс за основою.

**Рішення.** External content + тригери на вставку/видалення/зміну: текст не дублюється. Токенізатор
`unicode61 remove_diacritics 0` — регістр знімається, але «й»/«ї» не зливаються з «и»/«і». Кожне слово запиту —
рядок у лапках з префіксом за основою (`"кав"*`), слова через OR; запит — параметр SQL. Стоп-слова відкидаються.

**Чому / наслідки.** OR + BM25 дає результати й тоді, коли збіглась частина слів, а фрагменти з більшою
кількістю збігів ідуть вище — краще для hybrid. Префікс за основою — проста заміна стемера для української.
External content прив'язаний до rowid таблиці `Chunks`: після `VACUUM` індекс треба перебудувати
(`INSERT INTO ChunksFts(ChunksFts) VALUES ('rebuild')`), тому `VACUUM` без перебудови не робимо.

## DR-030 · Зберігання бекапів на сервері

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #80

**Проблема.** Де і як сервер зберігає зашифровані бекапи та як не дати користувачам доступ до чужих.

**Варіанти.** BLOB-колонка в SQLite; файли на диску з метаданими в БД; об'єктне сховище (S3).

**Рішення.** Файли в теці `Storage:RootPath`, ім'я — `{Guid}.lmbk`, яке генерує сервер; метадані (власник, розмір,
SHA-256, час) — у таблиці `Snapshots`. Запис іде в тимчасовий файл і перейменовується лише після успіху. Ліміт —
`Storage:MaxBackupBytes` (100 МБ): перевіряється і `Content-Length`, і фактична кількість байтів під час запису
(`413`). Будь-який запит до бекапу фільтрується за власником з токена; чужий бекап — `404`, як і неіснуючий.

**Чому / наслідки.** Великі бінарні дані не роздувають SQLite і читаються потоком. Ім'я файла не залежить від даних
користувача, а шлях додатково перевіряється на вихід за межі теки — path traversal неможливий. `404` замість `403`
не підтверджує, що бекап із таким id існує. Квоти на кількість і сумарний розмір — у DR-032.

## DR-020 · Хост застосунку: Generic Host і фоновий запуск ядра

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #70

**Проблема.** App має отримувати ядро через DI, не залежати від поточної папки і відкриватися навіть без моделі
або з недоступною БД. CLI бере модель відносно поточної папки, тому його запускають з кореня репозиторію — для
застосунку так не можна.

**Варіанти.** Власний `ServiceCollection`, як у CLI; Generic Host (`Microsoft.Extensions.Hosting`).

**Рішення.** Generic Host: конфігурація, логування, `IHostedService` для фонового запуску і впорядковане звільнення
сервісів «з коробки». Запуск ядра (міграції, вектори, повторна перевірка папок) — у `BackgroundService`, результат —
у `CoreStatus`. Відносний шлях до моделі шукається поруч із програмою, у теці даних користувача, а в Debug-збірці при запуску з репозиторію — ще й у його корені
(папка з `LocalMind.slnx`): у розробці модель (~450 МБ) не копіюється в `bin/`. Інші батьківські папки не
перевіряються, щоб чужий `C:\models\...` не підмінив модель. Контейнер з `ValidateOnBuild`.

**Чому / наслідки.** Вікно відкривається одразу, помилка запуску видна користувачу, а не валить процес.
Під час пакування модель кладемо поруч із програмою (`models/...`) — шлях з `appsettings.json` той самий.

## DR-021 · Оцінка пошуку: розмітка за документами, метрики за згорнутим списком

**Проблема.** Для порівняння BM25, semantic і hybrid (E1) і різних розмірів фрагмента (E3) потрібен датасет, який не
залежить від того, як нарізано текст.

**Варіанти.** Розмітка релевантних фрагментів; розмітка документів.

**Рішення.** Релевантність задається на рівні документів (шлях відносно `corpus/`, оцінка 1–3). Результат пошуку
(фрагменти) згортається до документів: береться перша поява. Метрики — Recall@k, MRR, nDCG@k з лінійним виграшем.
Для k документів просимо в пошуку `k × 5` фрагментів. `localmind eval` індексує корпус у тимчасову базу, не
чіпаючи бібліотеку користувача, і перед прогоном перевіряє, що модель доступна: Hybrid без моделі деградує до
keyword, а для експерименту це дало б хибні цифри.

**Чому / наслідки.** Id фрагментів змінюються при кожній індексації, а межі залежать від налаштувань E3 — розмітка за
фрагментами зробила б результати непорівнянними. Ціна: не видно, чи знайшовся саме потрібний абзац документа.

## DR-022 · Вхідні файли й модель: спільні ліміти, сигнатури, SHA-256

**Проблема.** Файл розміром у гігабайти читався в пам'ять цілком (ліміт був лише в `PdfParser`); текст з розширенням
`.pdf` чи DOCX-бомба доходили до парсера; підмінений `model.onnx` завантажувався без перевірки, хоча ONNX Runtime
виконує те, що в ньому описано.

**Варіанти.** Ліміт у кожному парсері; перевірка в одному місці перед парсингом. Для zip-бомби — лише заявлений
розмір записів чи фактично розпакований. Для моделі — хеш у скрипті завантаження чи ще й у конфігурації.

**Рішення.** `FileGuard` перед парсингом (розмір → сигнатура → zip-ліміти), `IngestionOptions` з трьома лімітами
(50 МБ файл, 2000 записів, 256 МБ розпакованого). Розпакований розмір рахується за фактично розпакованими даними з
достроковою зупинкою. Хеші моделі й токенізатора лежать у конфігурації (`ModelSha256`, `TokenizerSha256`), перевіряються
при завантаженні по байтах у пам'яті: файл читається один раз, хеш рахується по цих самих байтах, а ONNX-сесія й токенізатор
створюються з них, а не з файла за шляхом; порожній хеш — не перевіряти (експериментальні моделі).

**Чому / наслідки.** Один ліміт і одне повідомлення для обох шляхів індексації; завеликий файл хешується потоком, тож
не індексується щоразу наново. Хеші дублюються в `scripts/download-models` і `appsettings.json` — тест звіряє їх, щоб
вони не розійшлися. Перевірка 450 МБ моделі коштує ≈1 с при першому використанні, а під час створення сесії в пам'яті ненадовго
лежать і байти файла, і сама сесія (≈2× розміру моделі); масив не зберігається і збирається GC. Підміна між перевіркою
й завантаженням неможлива навіть там, де блокування файлів дорадчі (Linux, macOS), бо файл за шляхом після перевірки
не відкривається. Якщо файл зайнятий (його саме завантажує `scripts/download-models`), користувач бачить підказку,
а не сирий `IOException`.

## DR-031 · Клієнт бекапу: токени, знімок бази, відновлення

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #107

**Проблема.** Клієнту потрібно тримати сесію між запусками так, щоб токени не лежали відкритим текстом, робити
цілісний бекап бази під час роботи застосунку і відновлювати його так, щоб невдача не зіпсувала поточну базу.

**Варіанти.** Токени: відкритий файл; DPAPI на Windows і Keychain/libsecret на інших ОС; DPAPI на Windows,
на інших ОС — лише пам'ять. Знімок: копія файла; Backup API SQLite; `VACUUM INTO`.

**Рішення.** На Windows пара токенів зберігається у файлі `session.bin`, зашифрованому DPAPI (`CurrentUser` + власна
ентропія). На Linux і macOS — лише в пам'яті: після перезапуску треба увійти знову. Адреса сервера — лише HTTPS
(HTTP дозволено тільки для localhost). Клієнт сам оновлює access-токен (заздалегідь і після `401`); паралельні запити
оновлюють його лише раз, бо інакше сервер побачив би повторне використання refresh-токена й відкликав сесію.
Знімок — `VACUUM INTO` у тимчасовий файл поруч із базою, далі шифрування (DR-014) і upload. Відновлення: download →
розшифрування з перевіркою тегу → запис у тимчасовий файл → `PRAGMA integrity_check` і перевірка, що це база LocalMind
(є `__EFMigrationsHistory`, `Documents`, `SourceFolders`) → `File.Replace` поверх бази зі збереженням попередньої як
`.bak` → міграції; якщо міграції впали, попередня база повертається. Бекап опційний: без `ServerUrl` застосунок
стартує, а операції бекапу повідомляють, що сервер не налаштовано. Вихід виконується під тим самим локом, що й
оновлення токенів, тож паралельний refresh не відновить сесію після виходу.

**Чому / наслідки.** Keychain і libsecret потребують нативних залежностей, на які в проєкту немає часу, а «лише пам'ять»
безпечна за замовчуванням. `VACUUM INTO` дає цілісну копію в одній транзакції, навіть поки йде індексація. Неправильний
пароль, підміна чи зіпсований файл виявляються до будь-якої зміни бази. Залишкові ризики: відкритий знімок кілька
секунд лежить на диску поруч із базою (видаляється одразу, але без secure wipe); перед відновленням хост має зупинити
роботу з базою.

## DR-032 · Захист від перебору й переповнення сервера

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #104

**Проблема.** Без обмежень сервер дозволяє перебирати паролі з багатьох акаунтів, з'ясовувати через реєстрацію, чи є
такий email, заповнити диск бекапами й безмежно накопичувати записи refresh-токенів.

**Варіанти.** Перебір: лише lockout акаунта; ліміт запитів за IP; CAPTCHA. Реєстрація: `409` для зайнятого email;
однакова відповідь з листом-підтвердженням; однакова відповідь без листа. Диск: лише ліміт одного файла; квоти на
користувача.

**Рішення.** Реєстрація й вхід мають ліміт з однієї IP — fixed window, за замовчуванням 20 запитів за хвилину
(`RateLimiting:AuthPermitLimit`, `AuthWindow`); refresh, logout і `/me` — окремий м'якший (60, `SessionPermitLimit`), бо це
звичайна робота клієнта, а не перебір. Понад ліміт — `429` з `Retry-After` і ProblemDetails.
Lockout акаунта лишається тимчасовим (5 спроб → 15 хвилин, DR-016). Реєстрація зайнятого email повертає той самий
`201` без тіла, що й нова; акаунт і пароль власника не змінюються. Слабкий пароль усе одно дає `400`: Identity
перевіряє його раніше за унікальність, тож відповідь від існування email не залежить. Квоти на користувача:
`Storage:MaxBackupsPerUser` (20) і `Storage:MaxTotalBytesPerUser` (1 ГБ), понад них — `409`. Завантаження одного
користувача виконуються по черзі (замок у пам'яті на користувача навколо «перевірка квоти → запис файла → insert»):
без цього паралельні запити всі проходили б перевірку до першого insert, і квота не діяла б. Фонова служба раз на
6 годин видаляє refresh-записи, строк яких сплив понад добу тому.

**Чому / наслідки.** Ліміт за IP стримує і перебір паролів, і перебір email, не блокуючи чужі акаунти, а lockout
захищає конкретний акаунт від розподіленого перебору. Листів сервер не надсилає, тож людина, яка забула про свій
акаунт, побачить «успіх», а потім помилку входу — прийнятна ціна. Залишкові ризики: за NAT або проксі всі клієнти
ділять одну IP (за reverse proxy потрібні ForwardedHeaders — DR-033); зловмисник може навмисно блокувати чужий акаунт
на 15 хвилин; час відповіді реєстрації для зайнятого й нового email трохи різниться (insert проти відмови), тож
витік у принципі можливий за часом; клієнти за одним NAT ділять ліміт на вхід.

## DR-033 · Сервер у Docker за reverse proxy

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #105

**Проблема.** Сервер бекапу треба запускати однією командою, не вкладаючи секрети в образ, і так, щоб за reverse
proxy він бачив справжню IP клієнта (rate limiting, DR-032) і схему HTTPS.

**Варіанти.** TLS у самому контейнері (Kestrel із сертифікатом); reverse proxy на хості із завершенням TLS;
`ForwardedHeaders` з довірою до всіх; `ForwardedHeaders` лише від перелічених проксі.

**Рішення.** Образ збирається двома етапами (SDK → aspnet), працює не від root і слухає лише HTTP на 8080.
Ключ JWT передається змінною `Jwt__SigningKey`; без нього сервер (за валідацією з DR-017) і `docker compose` не
стартують. База й бекапи — в окремих томах. TLS завершує reverse proxy. `X-Forwarded-For` і `X-Forwarded-Proto`
сервер приймає лише від адрес із секції `ReverseProxy` (`KnownProxies`, `KnownNetworks`), з `ForwardLimit = 1`;
без налаштування заголовки ігноруються. Невалідна адреса зупиняє старт. Порт у compose відкритий тільки на
`127.0.0.1`.

**Чому / наслідки.** Довіра до всіх проксі дозволила б клієнту підробити `X-Forwarded-For` і обходити ліміт запитів;
тест це перевіряє. Сертифікати й їх оновлення — задача проксі, а не застосунку. Залишкові ризики: за замовчуванням
у compose довірена вся приватна мережа `172.16.0.0/12` (її слід звузити до адреси свого проксі); при `ForwardLimit = 1`
ланцюжок із двох проксі (CDN і nginx) дасть клієнтом найближчий із них, тож ліміт запитів стане спільним; образ тут перевірено
лише збіркою `dotnet publish` і розбором compose, повну збірку в Docker і запуск контейнера треба перевірити на
машині з Docker.

## DR-034 · Ролі User/Admin і аудит подій безпеки

**Дата:** 2026-11-11 · **Статус:** прийнято · **Issue:** #123

**Проблема.** Сервер потребує адміністратора (список користувачів, блокування) і журналу подій безпеки, але так, щоб
не з'явився шлях стати адміном через реєстрацію, а в журнал не потрапили секрети.

**Варіанти.** Адмін: той, хто першим зареєструє заданий email; адмін з пароля в конфігурації; окрема консольна
команда. Блокування: прапорець у власній таблиці; lockout Identity. Аудит: лише лог; таблиця в БД + лог.

**Рішення.** Ролі Identity `User` (отримує кожен після реєстрації) і `Admin`. Початковий адмін створюється на старті з
`Admin:Email` і `Admin:Password` (пароль — зі змінної середовища; обидва поля або жодне; пароль проходить звичайну
політику). Якщо такий email уже зареєстровано, його **не** підвищують, а лише пишуть попередження: інакше, хто першим
зареєстрував би цей email, став би адміністратором, бо email не підтверджується. Ролі потрапляють у access-токен
(claim `role`), але політика `Admin` додатково перевіряє БД (користувач існує, досі адмін, не заблокований), тож
позбавлення ролі чи блокування діють на адмін-ендпоінти одразу, а не через 15 хв. Ендпоінти `/api/v1/admin`: список
користувачів (з кількістю й розміром бекапів), блокування, розблокування, перегляд аудиту. Блокування — це lockout
Identity до `MaxValue` плюс новий SecurityStamp і відкликання всіх сесій; себе заблокувати не можна (`409`).
Аудит пишеться в таблицю `AuditEntries` і в лог: реєстрація, успішні й невдалі входи, refresh (успіх, відмова,
повторне використання), вихід, відкликання всіх сесій, завантаження й видалення бекапів, блокування, розблокування.
Запис містить код дії, користувача, виконавця, IP і причину з фіксованого переліку. Записи старші за
`Audit:RetentionDays` (180) видаляє фонова служба.

**Чому / наслідки.** Для невідомого email вхід пишеться без email: користувач міг ввести в це поле пароль, і він
потрапив би в журнал. Пароль, токени й будь-який введений текст у журнал не потрапляють (є тест). Збій запису аудиту
не ламає запит, а лише логується: доступність важливіша за повноту журналу. Користувачі, зареєстровані до цієї зміни,
не мають ролі `User`; на роботу API це не впливає, бо вимагається лише `Admin`. Залишкові ризики: адмін-акаунт, що
вже існує з іншою роллю, треба призначати вручну (у БД); журнал живе в тій самій БД, що й дані, тож зловмисник із
доступом до БД може його змінити.


## DR-024 · Каталог embedding-моделей для експерименту E2

**Проблема.** E2 порівнює embedding-моделі; потрібні кілька багатомовних (українська + англійська) моделей з ONNX,
відкритою ліцензією й запуском на CPU, які працюють через наш `OnnxEmbedder` без нового коду.

**Що підтримуємо.** `ModelTokenizer` — це XLM-RoBERTa SentencePiece (`sentencepiece.bpe.model`), а `OnnxEmbedder`
усереднює вектори токенів (mean pooling) і додає `token_type_ids`, якщо модель їх очікує. Отже, підходять моделі на
словнику XLM-R з mean pooling. Файл токенізатора в усіх обраних моделей той самий (SHA-256 `cfc8146a…`).

**Рішення.** Чотири моделі (fp32, файл `onnx/model.onnx`), каталог — секція `LocalMind:ModelCatalog` в `appsettings.json`
(назва, репозиторій і повний коміт Hugging Face, ліцензія, розмір, SHA-256 моделі й токенізатора, розмірність, ліміт
токенів, префікси):

| Модель | Ліцензія | Розмірність | ONNX | Префікси | Ліміт токенів |
|---|---|---|---|---|---|
| `multilingual-e5-small` | MIT | 384 | 470 МБ | `query: ` / `passage: ` | 512 |
| `multilingual-e5-base` | MIT | 768 | 1,11 ГБ | `query: ` / `passage: ` | 512 |
| `paraphrase-multilingual-MiniLM-L12-v2` | Apache-2.0 | 384 | 470 МБ | немає | 128 |
| `paraphrase-multilingual-mpnet-base-v2` | Apache-2.0 | 768 | 1,11 ГБ | немає | 128 |

Модель обирається назвою: якщо `LocalMind:Embedding:ModelName` є в каталозі, опис моделі (токенізатор, хеші,
розмірність, ліміт токенів, префікси) береться з каталогу, а шляхи — лише якщо не задані
(`LocalMind__Embedding__ModelName=multilingual-e5-base`). Модель, якої немає в каталозі, — власна — лишається як
налаштована, з усіма полями вручну. `scripts/download-models.sh|.ps1 [модель|all]` завантажує модель у `models/<назва>/`
за закріпленим комітом і перевіряє SHA-256; без параметра — `multilingual-e5-small`. Хеші в скриптах і в каталозі
дублюються, тест `ModelCatalogTests` звіряє їх, а також повноту каталогу (без завантаження моделей у CI).

**Ліміт токенів і розмір фрагмента.** Моделі `paraphrase-*` навчені на 128 токенах, тому в каталозі ліміт 128, і
стандартний `ChunkSizeTokens=256` на них не пройде перевірку запуску (повідомлення назве обидва параметри). Для E2 на
таких моделях ставимо `ChunkSizeTokens` ≤ 120; щоб порівняння було чесним, E2 слід проганяти й на e5 з таким самим
розміром фрагмента.

**Чому не інші.**
- `Snowflake/snowflake-arctic-embed-m-v2.0`: CLS pooling замість mean (потрібна зміна `OnnxEmbedder`), у репозиторії
  немає `sentencepiece.bpe.model` (лише `tokenizer.json`), тож збіг словника з нашим токенізатором довелося б доводити.
- `BAAI/bge-m3`: ONNX 2,3 ГБ з окремим файлом даних, CLS pooling; надто важкий для CPU-застосунку.
- `LaBSE`: токенізатор BERT WordPiece, не підтримується.
- Квантовані (int8) файли: не беремо — залежать від набору інструкцій CPU (AVX512-VNNI), якість окремо не перевірено.

**Чому / наслідки.** Каталог у конфігурації, а не в коді, дозволяє додавати модель без перекомпіляції, але лише в межах
підтримуваного токенізатора й pooling. Нові завантаження — сотні мегабайтів у `models/` (поза Git): усі чотири
моделі разом ≈ 3,2 ГБ.
